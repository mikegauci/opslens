# Runtime and local setup

## Decision

Select Node 24 LTS with Hono's Node adapter for the foundation. One process serves the Vite production assets, `/foundation`, and `/api/*` on one origin. Relative API URLs keep previews self-contained. PostgreSQL is accessed only by the API through `pg`; the browser has no database credentials. The checked-in production entrypoint is `pnpm start` after `pnpm build`, with the repository root as its working directory.

This spike proves the selected **Node runtime locally and in CI**. It does not claim a hosted preview, provision a cloud account, or verify a provider's ingress buffering, TLS, regional latency, pooling or cold starts. Select/provision the managed Node/container host before a public demo, then repeat these same checks through its real URL. Do not call local evidence cloud deployment evidence.

| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Portable Node service | Hono `@hono/node-server`; Vite files served by the same process. Native `pg`, explicit pool/timeouts and ordinary SSE. Host must support Node 24, a long-lived process and unbuffered streaming. Asset CDN, process scaling and managed ingress remain host decisions. | Selected runtime; reproducible without a vendor account.                               |
| Sites                 | The installed Sites skill specifies a Cloudflare Worker runtime, HTTP external connections and no raw TCP. ## Fresh checkout

1. Install/use Node from `.nvmrc` (`nvm install && nvm use` if using nvm), then `npm install --global pnpm@12.11.2`.
2. `pnpm install --frozen-lockfile`.
3. `cp .env.example .env` and `docker compose up -d --wait db` with a running Docker engine. The database binds only to loopback, uses a named volume and uses development-only credentials. Stop it with `docker compose down`; add `--volumes` only when intentionally discarding its local data.
4. `pnpm db:migrate && pnpm db:login && pnpm db:seed 100000 && pnpm db:verify`. Migrations and seeds use `MIGRATION_DATABASE_URL`; the API uses the separate restricted `DATABASE_URL`. Repeat migrations/seeds safely to select the same dataset; seed `10000` for the smaller comparison. Generated CSVs are optional: `pnpm data:generate`; their hashes are committed in `data/manifest.json`. See [data conventions and oracle](../data/README.md) and [schema/access review](../supabase/README.md). Use a disposable development database: seeding atomically replaces the active dataset.
5. `pnpm build && pnpm start`, then visit `http://127.0.0.1:3000/foundation`. It shows the real `SELECT 1` result and completion of a finite two-event diagnostic stream. It is not a dataset or live AI response.
6. For editing with hot reload, leave the API running and use `pnpm --filter @opslens/web dev` in another terminal. Vite proxies `/api` to port 3000. `pnpm dev` is a convenience build-and-start of the production spike, without hot reload.

An existing PostgreSQL 17 instance also works: create a disposable `opslens` database and set `DATABASE_URL` accordingly. Local verification used Homebrew PostgreSQL 17.11 because Docker's daemon was unavailable. No Supabase resource is needed. PLAN-03 establishes the private schema, checksummed migration runner, repeatable 10k/100k seeds and restricted `opslens_app` login. The local development owner is only for migrations/seeds. Supabase CLI 3.0.0 scaffolded the first migration; running the app does not require that CLI or its Docker stack. Hosted Data API exposure and advisors remain unverified.

Required runtime server variable: `DATABASE_URL` (restricted application login). Data setup/check commands also require server-only `MIGRATION_DATABASE_URL` (owner login). `pnpm db:login` configures the application password from `DATABASE_URL` on the same database; production secret provisioning is outside this local workflow. Optional: `PORT` (3000), `HOST` (`127.0.0.1`; use `0.0.0.0` behind managed ingress). Node loads ignored `.env`; real hosting injects secrets. Never place server variables in Vite-prefixed variables. Pool: at most five connections, three-second connect/statement timeouts. Use a provider's TLS-verified/pooler connection string in hosting; do not disable certificate verification. Budget connection counts against instances before scaling.

## Verification and contracts

Run `pnpm exec playwright install chromium` once on a supported OS; Linux CI installs browser system dependencies too. On this macOS 13 machine the current bundled Chromium is unsupported: use installed Chrome with `PLAYWRIGHT_CHANNEL=chrome pnpm check` (and the same variable for `pnpm benchmark`). This is an explicit local fallback, not evidence for the pinned CI browser. Keep the database running, stop any app on port 3000, then run `pnpm check`.

- Biome checks code/style and TypeScript checks all packages.
- Vitest covers integer money, API availability/error responses, SSE ordering, and deterministic hashes/story properties at both dataset sizes. `data:check` rejects committed manifest drift. `db:verify` reconciles every stored row/hash, independently authored fixture SQL/expected values, schema constraints, private-schema grants/RLS and actual application write/DDL denials. API unit tests inject the database boundary; the production browser smoke performs the actual PostgreSQL query.
- Playwright starts the production Node server, verifies the route → generated client → API → PostgreSQL → UI flow, error/retry recovery, and that the first HTTP stream chunk precedes completion. No AI key or remote provider is needed.
- API schemas are declared once with Hono/Zod. `pnpm contracts:generate` exports OpenAPI and generates `schema.d.ts` using openapi-typescript's Node API. Commit both outputs. `pnpm contracts:check` regenerates and fails on tracked changes. Do not hand-edit generated files. [Generator API](https://openapi-ts.dev/node), [typed fetch client](https://openapi-ts.dev/openapi-fetch/).
- Unknown API routes return JSON 404, never SPA HTML. Database failure returns a non-sensitive 503; startup without `DATABASE_URL` fails clearly.

CI runs the same checks on Ubuntu 24.04 with a real PostgreSQL service and Chromium. Before the gate it simulates Data API roles, migrates twice, seeds each size twice, verifies 10k and leaves 100k selected for the full gate. Official Node-24 action revisions are pinned by SHA. There are no live AI calls or dummy badges. Full dashboard, accessibility and AI checks are added with those capabilities. CI artifacts retain failing browser traces. Dependency versions are exact, peers were checked against registry metadata, and the lockfile is required; upgrades repeat this verification.

## Initial performance conditions

[Raw baseline](foundation-baseline.json), captured 6 November 2026, records the hardware, browser, OS, runtime and every round trip. This is one local observation on a four-thread Intel i7-7660U with 16 GiB RAM, macOS 13.7.8, Node 24.20.0, Chrome 156, loopback PostgreSQL 17.11 and no network/CPU throttling. The server was already running; the fresh browser's first journey warmed the pool and included the deliberate 200 ms stream delay. There are **zero dataset rows**, so this establishes no 10k/100k query or production performance claim.

Observed first journey through database and stream completion: 1,907 ms; DOMContentLoaded: 394 ms; document plus resource transfer: 230,848 bytes without an ingress compressor. Ten subsequent Node health HTTP round trips: median 13.2 ms, range 6.9–98.1 ms (first includes a fresh HTTP connection). These are end-to-end connectivity timings, not isolated SQL timings or a statistical service target. Vite emitted 227.88 kB JavaScript (71.61 kB estimated gzip); the server currently sends uncompressed assets.

Initial review guardrails: keep this diagnostic entry's JS under 250 kB uncompressed and explain any comparable baseline regression over 20% in the PR; these are review thresholds, not CI timing assertions. Rebaseline deliberately when real screens and data arrive. PLAN-03/04 add representative SQL/query plans; PLAN-06/07/13 measure the full 10k/100k interactions, memory and transfer with server region and cold/warm conditions. Do not use local timings as cloud budgets.

To reproduce, run the production server and database, then `pnpm benchmark` in another terminal (use the Chrome variable above on this Mac). It overwrites the baseline JSON and writes review screenshots to `/tmp`. Desktop (1280 px) and mobile (390 px) snapshots were visually reviewed with no clipping: [desktop](images/foundation-desktop.png), [mobile](images/foundation-mobile.png). This does not claim a full accessibility audit or screen-reader review.

## Overview — PLAN-06

Open `/` after building/starting; `/foundation` retains the original runtime diagnostic. The overview defaults to 22–28 September 2026 UTC in the fixed dataset, compared with 15–21 September. Apply inclusive calendar dates, brand and provider using the labelled native controls; canonical UTC timestamps are persisted in the URL. Invalid/repeated filters require an explicit correction/reset. Out-of-window scopes produce an actionable API error rather than zero figures.

Each panel starts independently, validates network data with the browser-safe shared schemas and retains its own original scope/as-of while stale. Superseded requests are aborted and have a separate effect-lifetime ownership guard. All drill-downs pause during stale/error/loading states or a dataset-hash mismatch. Refresh the affected panel (or all mismatched panels) to recover. Chart links open the matching transaction scope in `/activity`.

The build-plan chart stack was a proposal. For these two bounded series (at most 90 days/three providers), PLAN-06 uses native SVG/CSS with named links and semantic data tables instead of adding ECharts. No client aggregation or downloaded transaction dataset is used. The React request hook is intentionally local; shared component extraction and Storybook remain PLAN-08. Existing UI shell/tokens are reused/refined without introducing a second design system. Installed React declarations and the existing generated-fetch/schema APIs were checked; no third-party version changed.

The overview entry is now 332.03 kB JavaScript (101.52 kB estimated gzip), compared with the 227.88/71.61 kB diagnostic baseline. This deliberate ~46% uncompressed increase includes the real dashboard, generated analytics calls and browser runtime validation (Zod), so exceeds the foundation-only 250 kB review threshold. The production adapter still does not apply ingress compression. A chart framework was avoided for the small bounded series; future splitting and actual transfer/interaction budgets belong to the complete application performance work. Hosting remains unverified.

PLAN-06 browser tests include a rollback-only oracle HTTP adapter plus a separate production 100k journey. Exact expected figures come from the original fixture/literal checks, never production calculations. Failure traces remain in `test-results/`. ## Activity — PLAN-07

Open `/activity` directly or follow a provider or day link from Overview. The default table exposes one complete 100-row page. Select **Virtual scrolling** to load additional batches into a window of up to 1,000 rows, then continue at the next offset in pages. The server handles filtering, sorting and paging in both views. Choose placement basis to inspect pending or void transactions. The date inputs and shareable URL use canonical UTC timestamps with an exclusive end.

After `pnpm build`, run `pnpm benchmark:activity` with the restricted connection and the 100k seed selected. The script starts a separate loopback server on port 3107. On this Mac, set `PLAYWRIGHT_CHANNEL=chrome`. The output records browser rendering and heap, HTTP transfer and separate database query plans in `docs/benchmarks/activity-100000.json`.
