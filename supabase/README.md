# PostgreSQL schema and access review (PLAN-03)

These are portable PostgreSQL 17 migrations under the planned Supabase directory. The initial file was scaffolded with Supabase CLI 3.0.0 `migration new`. No Supabase project, REST API, CLI migration history or local Docker stack is provisioned. The small `pnpm db:migrate` runner applies sorted SQL files in one transaction under an advisory lock, tracks SHA-256 in `opslens_meta.migrations`, skips matching files, and rejects edits to applied migrations. Do not mix its history with Supabase CLI migration application; reconcile histories before adopting managed Supabase.

Use a separate privileged migration/seed login via `MIGRATION_DATABASE_URL`; the Docker development owner is `opslens`. Only migration provisioning requires CREATE ROLE. The owner may bypass RLS for seeding; its credential must never be used by the running API. `DATABASE_URL` identifies `opslens_app`. `pnpm db:login` explicitly sets that role's password from the application URL without storing it in migrations or printing it. Example passwords are development-only; hosted secret provisioning is a separate step.

The application role has no superuser, database/role creation, replication, bypass-RLS or inherited memberships. Analytics access consists of USAGE on `opslens_private` and explicit SELECT on the two analytics tables. It owns no application objects. RLS is enabled with a SELECT policy for this role; all synthetic rows are readable. The analytics tables have only SELECT policies for the runtime role. Read-only transaction defaults and a three-second statement timeout add defense in depth; verification disables the read-only default and proves writes/DDL still fail through grants. Every denial probe is rollback-only, including an unexpected successful probe.

`opslens_meta` is not readable by the application. PUBLIC receives no private-schema/table privileges or future table/sequence grants. Future objects do not automatically receive application SELECT. PUBLIC CREATE on `public` is revoked. There are no project tables/functions in `public`, no browser database connection, and no Data API exposure in this Node deployment.

If `anon`, `authenticated` or `service_role` exist, migration explicitly revokes private-schema/table access from them. CI creates equivalent roles (including service_role BYPASSRLS) before migration and verifies their effective grants. This checks PostgreSQL permissions, not a hosted Supabase Data API setting. Before deploying Supabase, keep `opslens_private` and `opslens_meta` out of Exposed schemas, review actual dashboard/role memberships/default grants, disable Data API if unused, and run platform advisors. Exposed tables require both deliberate grants and RLS. No hosted configuration/advisor result is claimed here.

Reviewed 6 November 2026 against [Supabase API security](https://supabase.com/docs/guides/api/securing-your-api), the [changelog](https://supabase.com/changelog) (including automatic-exposure changes), [PostgreSQL 17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), and [default privileges](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html). The 17.11 extension changes do not affect this schema: it installs no extensions, custom operators or extension indexes. Physical query indexes/plans await representative analytics queries in PLAN-04; the ID primary key is the only index here.

## Copilot quota (PLAN-11)

The private quota table has RLS enabled and no direct grants to the application or Data API roles. A single security-definer function uses an empty search path, qualifies its table and lock references, and grants execution to `opslens_app`. It reserves one public request against the visitor and global UTC-day counters in the same short transaction. The runtime uses an explicit read-write transaction for that call. Analytics retain their read-only defaults and grants.

On a disposable migrated and seeded test database, `OPSLENS_QUOTA_TEST=1 pnpm db:verify:copilot` exercises concurrent calls across pools, a new pool after exhaustion, counter retention, and effective role grants. It requires an empty quota table and clears the test counters on exit. CI runs it against its disposable service.
